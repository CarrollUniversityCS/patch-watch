# Audit — 2026-10-23, against the goal "publishable work on how local Wisconsin entities reacted to PHP2Shell"

Audited at `eca4efd` (working tree clean). Read every file in `src/`, `docs/`, `scripts/`,
`reports/`; ran the suite (**305 passed** in a fresh venv, not the 303 the docs quote); probed
edge cases against the loopback mock rig; checked the vulnerability facts against php.net;
counted Wisconsin domains in today's public CISA list. No request was sent to any .gov host.

## Verdict

The engineering is careful and the safety posture is good. **But the repo does not yet
answer the stated question, and three things in it would make published numbers wrong.**

1. **Scope mismatch.** Everything here — frame, sample, IRB note, public notice — describes
   a *national* stratified pilot. Nothing is Wisconsin-specific. The 319-domain sample
   holds roughly **9–10 Wisconsin domains** in expectation (see the table below). That is
   not enough to say anything about Wisconsin.
2. **A classification bug hides every broken-certificate site** (finding C1). The
   `https_unverified` phase reads their headers, then the classifier throws them away.
3. **No pre-fix baseline exists, and none can be collected now.** The fix shipped
   2026-10-21. Gate A is still closed. "How they reacted" needs a "before", and the only
   remaining source of one is archived crawl data (see "Study design").

## Correctness findings (code)

All confirmed by running the code, not by reading it alone. The probe script is outside the
repo; the cases are easy to turn into tests.

**C1 — HIGH. Broken-cert sites are classified `NO_RESPONSE` even when their headers were read.**
`src/fetch.py:562-572`: phase 1 sets `obs.error_type = "cert_error"`. The unverified retry
then succeeds (status 200, `X-Powered-By: PHP/8.3.35`), but nothing clears `error_type`. The
`http_fallback` branch does clear it, at `:591`. `classify.classify()` returns
`NO_RESPONSE` for any non-empty `error_type` (`src/classify.py:248`). Probe result:
`status=200 err=cert_error xpb=['PHP/8.3.35'] -> NO_RESPONSE`. The existing test
`test_rule2_cert_failure_gets_one_unverified_retry_and_no_more` checks only the status and
the send count, never the class, so it misses this. Small municipal sites with broken
certificate chains are common, so the bias falls on exactly the population this study cares
about. It also makes the public page's justification for phase 2 untrue in practice.
*Fix:* clear `error_type` before the unverified attempt, as at `:591`, and keep
`cert_error=True`. Add a test that asserts the class.

**C2 — MEDIUM. Redirect-limit responses are classified `NO_RESPONSE`.**
`error_type="redirect_limit"` / `"redirect_no_location"` is set on a real HTTP response
(status 302, headers present) and goes into the "never reached HTTP" class. These sites
did respond.

**C3 — MEDIUM. "Not measured" outcomes go into substantive classes.**
- Blocklisted (opted-out) domains → `error_type="skipped_blocklist"` → `NO_RESPONSE`.
  Kill-switch-halted domains → `NO_RESPONSE`.
- A 403 from a WAF that blocks our user agent → `NO_PHP_EVIDENCE`.

`docs/project_page.md:74` promises that a site that refuses us "is recorded as 'not
measured'". No such class exists. Both of these inflate denominators. Opt-outs counted as
unreachable also leak into the published counts. *Fix:* add a `NOT_MEASURED` class (or
exclude these rows from every denominator) and report how many there were.

**C4 — MEDIUM. A partial version is a guess, which breaks hard rule 9.**
`PHP/8.3` parses as `(8,3,0)` and is classified `VULNERABLE_BY_VERSION`
(`src/classify.py:102-113`, "patch number absent, treated as .0"). It should be
`UNPARSEABLE` or flagged as ambiguous.

**C5 — MEDIUM (safety doc ≠ code). The abuse flag is not checked between requests.**
`docs/OPERATIONS.md:79` says the flag is checked "again between requests".
`KillSwitch.check_external()` is called only in `pipeline.preflight()` and at the start of
`capture()`. `Crawler.fetch()` checks only `self.kill.tripped`. If someone drops the flag
mid-run, it does nothing until the next run. Either call `check_external()` inside
`fetch()` (it is cheap) or correct the document. The code fix is better: this is the
operator's emergency stop.

**C6 — LOW.**
- `8.6.0RC1`–`RC3` (pre-fix release candidates) count as `PATCHED_UPSTREAM` through
  `is_newer_branch`.
- `X-Powered-By: PHP-FPM` / `phpBB` → `UNPARSEABLE` rather than evidence-only.
- The kill-switch window counts phases, not requests (hops are excluded), but the docs say
  "requests".
- `detect_changes()` uses the latest 13 rows, so re-running detection on a snapshot more
  than 13 runs old finds no prior row. This affects backfills only.

## Accuracy of the docs and the claims

- **Vulnerability facts: verified.** php.net confirms 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35,
  the two CVE/GHSA IDs, the 14:00 UTC schedule, and the 7.4–8.1 source backports.
  **Not verified:** the `versions.py` / `classify.py` docstrings attribute a remirepo
  warning to "the PHP project", but php.net does not mention remirepo. Cite the real source
  or drop the claim.
- **New: CVE-2026-115560 (php.net, 23 Oct).** It is in the same session upload-progress
  area as CVE-2026-109619, and its fix comes in the *next* regular release. A second
  fixed-version threshold may be coming. `versions.py` should get a dated note now, and
  the analysis must say which threshold "patched" means.
- **Configuration mitigation is invisible.** `session.upload_progress.enabled=0` is an
  advertised partial mitigation. "Vulnerable by version" therefore means exactly that, not
  "exploitable". The publication must say so.
- **Stale or contradictory text:**
  - `README.md:28` says "nine classes"; the code has eight.
  - `reports/STATUS_GATE_A_2026-10-23.md:141-142` says Gate A "needs either"; since
    `eca4efd` it needs both.
  - `src/config.py:29` mentions a "marker file"; it is an environment variable.
  - Test count: 303 in the docs, 305 in the suite.
  - `classify.py:144` cites `docs/analysis_plan.md`, which does not exist.
  - The "mission brief" that every hard rule cites is not in the repo.

  For a publication, the brief and the analysis plan need to be in the repo and dated
  **before** data collection. That makes them your pre-registration.
- **Reproducibility:**
  - There is no `requirements.txt` or lockfile, and the cookie fix depends on httpx 0.28.1
    behaviour. Pin it.
  - All paths are Windows paths (`.venv/Scripts`, `C:/Users/...`).
  - `data/` is empty in this checkout. The frame exists only on one machine.
  - Today's CISA list has **16,945 rows**, so `frame.py build` hard-fails on a fresh
    download (it expects 16,935), as designed. You must keep the 2026-10-22 raw file or
    record the `cisagov/dotgov-data` commit hash it came from. Without one of those, nobody
    can reproduce the sample.

## Wisconsin: the study design gap

Wisconsin nonfederal .gov domains in today's CISA list (843 total):

| Type | WI | Share of national type | Expected in current 40/stratum sample |
|---|---|---|---|
| City | 668 | 7.2% | ~2.9 |
| City/County – Election | 53 | 7.4% of Election stratum | ~2.9 |
| County | 61 | 2.2% | ~0.9 |
| State | 31 | 2.1% | ~0.9 |
| Special district | 20 | 1.8% | ~0.7 |
| Tribal | 10 | 3.5% | ~1.4 |
| School district | 0 | — | 0 |

What a Wisconsin study needs:

1. **A Wisconsin census, not a sample.** 843 homepages, one GET each, is less traffic than
   the national design already contemplates. That makes it feasible.
2. **A coverage statement.** Most Wisconsin local government web presence is not on .gov:
   school districts are on `k12.wi.us` or `.org`, and many towns and villages are on
   `.wi.us`, `.org` or `.com`. The study can only claim ".gov-registered Wisconsin
   entities", and the paper should say so. Many WI `.gov` names also redirect off-domain to
   the legacy site. The crawler records these and does not follow them. That is correct
   under rule 2, but it means the classification is of the `.gov` front door, not the site.
   Report the off-domain count.
3. **Small-cell suppression.** Tribal (10), special district (20) and county-election (4)
   cells are small enough that "3 of 10" approaches identifying a specific government. That
   breaks the public promise of no per-site results. Suppress cells under about 10, or
   merge them. Tribal nations deserve particular care as sovereign governments: consider
   excluding them, or reporting them only inside a merged cell.
4. **A pre-fix baseline from archives, with no traffic to the sites.** Common Crawl WARC
   response records keep the original HTTP headers, including `X-Powered-By`. A crawl from
   September or early October 2026 gives a "before" for whichever WI domains it captured.
   `versions.py` already anticipates this with `PRIOR_RELEASES`. Without it, the first
   snapshot is at t0+3 days at the earliest, and the paper can only describe the state of
   things and later changes, not the initial reaction.
5. **Speed.** Patch adoption is front-loaded, and every day Gate A stays closed loses that
   signal. Exploitation began 2026-10-17, before disclosure.
6. **Governance updates before any Wisconsin collection.** `IRB_INQUIRY_NOTE.md` and
   `project_page.md` describe a national 319-domain pilot. A Wisconsin census changes the
   population and the request volume, so revise both, and get the IRB determination (still
   pending) before Gate A.
7. **Disclosure before publication.** Exploitation is active, so tell the people who can
   act before the aggregates go out: the Wisconsin Cyber Response Team / DOA, or MS-ISAC.
   They can notify the affected entities without you publishing or handling a list. The
   `security_contact` column should stay unused unless the IRB approves direct
   notification.

## What is solid and should stay as it is

- The safety controls: two-key Gate A, the per-domain budget with an independent ledger
  audit, same-root redirect containment, the cookie fix with a regression test, a 64 KB
  body cap with no stored bodies, and a self-identifying user agent.
- Classification rules: integer-tuple version comparison, distro suffixes treated as
  ambiguous rather than vulnerable, and hidden versions never counted as patched.
- Change detection that separates flapping from upgrades.
- A frame tied to a hashed public list.
- The `STATUS` document's habit of correcting its own earlier claims in public. Keep doing
  that in the paper's limitations section.

## Recommended order

1. Fix C1–C5, with a test per finding that asserts the **class**, not only transport facts.
2. Commit the brief and an analysis plan: the Wisconsin census design, the definition of
   `NOT_MEASURED`, the suppression rule, and the threshold policy for CVE-2026-115560.
3. Pin dependencies. Archive the raw CISA file or its commit hash. Build a WI frame
   alongside the national one.
4. Update the IRB note and the notice page for Wisconsin scope, and send the IRB note.
5. Pull the Common Crawl baseline for WI domains (passive).
6. Gate A, then snapshots.
